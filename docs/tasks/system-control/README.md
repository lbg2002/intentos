1. 阅读本文件、[任务清单](BACKLOG.md)、[接口与安全契约](CONTRACTS.md)、[验收矩阵](ACCEPTANCE.md)。
2. 核对当前分支、工作树、远端最新提交与仓库 AGENTS.md。用户未提交改动必须保留。基线可能前进，逐项判断任务是否已经完成。
3. 默认先完成 SC-01、SC-02，再完成 SC-03/SC-04；之后进入 SC-05–SC-10。跨包接口先定契约再编码。
4. 每次只承诺选定工作包，交付实现、回归测试、文档与提交。未完成其他包继续标记待开发。
5. 最终更新 [状态与交付记录](STATUS.md)，写清已实现、实测、未测、阻塞与下一任务。

## 开发纪律

- 复用 Rust 核心、CapabilityBroker、PolicyEngine、TurnEffectLedger、ChangeSet、AgentEvent。禁止新建绕开策略的 CLI/UI 执行通路。
- 先复现失败，再实现，再验证；本地风险分析不能由模型结论替代。禁止为消除测试失败而放宽断言、默认批准或去掉沙箱。
- 对协议/存储改变给出版本、旧客户端行为、迁移、回退。新执行能力默认关闭直到必要门槛通过。
- 正常开发可在隔离 fixture 中测试；重启、格式化、真实宿主包安装、停服务等有破坏性验证须使用明确允许的可恢复测试机。
- 批准危险动作不等于系统认证完成；不保存 sudo 密码、不提供任意 root shell。
- 本地测试、模拟桌面、真实 Ubuntu/Wayland/X11、性能数据分别标注。缺少内核隔离时记录阻塞，不宣称安全用例通过。
- 提交用 `feat/fix/test/docs(scope)`，每个工作包保持可审阅；push 前检查 diff、测试结果和远端头部。远端前进则重新整合，不 force push。沿用用户已授权的 GitHub 同步范围。
- 任务完成提交模板：问题与前后行为；接口变化；测试命令/结果；环境限制；恢复办法；剩余任务。
