# AIOS 代码审查与目标交付方案

> 基于 `c34047fe8e74960b00bd8c33eb3f88135308db0d` 审查。本文补充既有设计，不改变 Ubuntu/GNOME 用户态认知壳层定位。
> 文档日期：2026-11-16（客户端日期）。设计文档的 v0.3 是文档版本，不代表软件已交付 v0.3。

## 1. 产品目标与验收方法更新

AIOS 的交付单位应为用户目标闭环：**理解目标 → 找到授权资源 → 制定步骤 → 审批 → 执行 → 读取环境证据 → 汇报与恢复**。
优先保证闭环可信，再扩大工具数量。Schema 字节下降、路由语料准确率、命令退出码分别衡量成本、路由、调用结果，不能替代目标成功率。

每个目标必须写清：前置条件、授权作用域、每个子目标、独立后置检查、证据来源与时间、失败状态、可撤销范围、无法撤销的影响。
例如「恢复论文工作区」需要分别确认文档、代码仓、终端目录和勿扰状态；应用启动请求返回成功只能说明已请求，不能证明文档已打开。

证据等级：

| 证据 | 能支持的结论 | 限制 |
| --- | --- | --- |
| 能力发现/模型文本 | 可用工具或执行建议 | 不证明执行发生 |
| 请求已接受、退出码为零 | 调用已发送或执行器已退出 | 不自动证明目标达成 |
| 账本 `Passed` 步骤 | 指定能力参数的步骤已通过该能力的验证 | 不等于任意用户目标成功 |
| 环境读回 | 文件存在/非空、观察到进程等具体谓词 | 文件存在不证明内容正确；进程存在不证明目标文档已打开 |
| 目标专属检查 | 内容、文档位置、设置值与预期一致 | 应报告采样时间、适用范围与无法观察的部分 |

统一完成状态沿用现有协议，不新建平行状态机：`Completed` 需要目标证据；`RequestedUnverified` 保留待观察事实；`PartialCompleted` 列出未完成子目标；`VerificationFailed` 明确失败。账本记账、目标验证、用户展示必须保持一致。

## 2. 代码审查结论

审查重点覆盖路由/结构化意图、动态元工具、回合账本/审批续接、终端分级与沙箱、文件边界、隐私记忆、项目/工作流、主动任务、Web/IPC 入口和已有测试。此为重点代码审查，不是全平台安全认证。

### 已有且应继续复用的基础

- `backend_bridge/` 已具备统一桥接、WAL 步骤状态、预算与审批断点；继续沿用 Broker 和账本，禁止另建第二条执行通路。
- `intent_engine/` 有结构化目标与未决子句；`meta_tools.rs`、`capability_snapshot.rs` 有渐进工具发现；这些适合作为多步骤目标执行的入口。
- `terminal_agent.rs` 与 `crates/sandbox/` 有本地风险分级、参数数组、无网络沙箱和撤销计划，不能用模型的效应声明降低本地风险等级。
- `memory_hub/` 已有情景、实体、文档大纲与习惯；`execution_hub/project_memory.rs` 已有项目发现和记忆候选；`skill_workflow.rs` 已有工作流学习/执行。M3 应补齐生命周期和统一查询，而非从零重写。

### 本轮落实的问题

| 优先级 | 代码位置 | 问题与影响 | 本轮改动 |
| --- | --- | --- | --- |
| P0 | `web_shell.rs` | HTTP 直接调用 `handle_trusted_ui_rpc`，缺少 Host/Origin 检查；回环监听本身不能阻止恶意网页来源和 DNS 重绑定 | 全路由 Host 回环白名单、浏览器同源和 Fetch Metadata 检查；服务拒绝非回环绑定 |
| P1 | `meta_tools.rs::execute_task_verify` | 应用进程未观察到时，以历史启动记录判定通过 | 启动账本仅作诊断信息；缺少进程观察即不通过该谓词 |
| P1 | 同上 | `succeeded` 包含 `RequestedUnverified`，却被计入已验证步骤 | 只计入 `succeeded && verification_status == Passed` |
| P1 | 同上 | 失败后任意同能力调用成功都能掩盖原失败，例如 A 文件查询失败、B 成功 | 恢复要求同能力、同规范化参数和 `Passed` |
| P1 | 同上及元工具包装层 | 数据 `verified:false` 与外层 `Exited/Passed/0` 矛盾 | 失败返回 `VerificationFailed/VerificationFailed/1`；无检查证据时显式列出失败原因 |

兼容性：沿用工具参数和返回数据主体；失败状态更严格是有意修复。Web/GTK 本地无 Origin 客户端继续可用；浏览器须使用页面同源地址。远程直连 `--web-listen 0.0.0.0` 不再支持，远程访问需另行设计认证、授权与传输协议。

### 尚未解决的边界与风险

1. `task.verify` 仍是指定谓词检查器，不是自然语言目标的通用证明器。进程匹配使用 `/proc/comm` 提示，文件只检查存在/非空；后续必须增加稳定应用身份、目标内容/文档位置检查，避免名称子串、陈旧产物带来误判。
2. 文件授权检查与 metadata 读取不是同一个原子操作，不能将其宣传为 `openat2` 全链路验证；目标验证需复用安全文件句柄和禁止 symlink 的路径解析。
3. Web 同源检查不认证同 UID 本地进程。`ipc.rs` 的 UID 和 worker 名称排除亦非抵御任意同 UID 恶意代码的完整认证机制；不能仅凭进程名称黑名单宣称可信客户端强认证。
4. `execution_hub/project_memory.rs::with_store` 读取也可能重写 JSON，且写入错误被忽略。M3 需分离读写、原子持久化、传播错误并验证隐私链路；不能认为所有记忆都已统一在 SQLite。
5. `execution_hub/drive_scheduler.rs` 有规则、触发与防抖判断，但无独立后台监听/调度循环；不代表 M4 的真实事件总线已交付。
6. 尚无仓库 `.github/workflows/`。建议在确认 Ubuntu 系统依赖与沙箱运行能力后增加分层 CI；容器不能执行的 bwrap 测试须明确失败/条件，不以静默跳过冒充安全验证。
7. README 的固定测试数量、兼容平台和性能数字是历史记录，应附运行环境与提交。`Cargo.toml` 的 Apache-2.0 与 README 的 MIT 声明存在冲突，需由维护者结合原始授权决定，本轮不擅自变更许可证。

## 3. 更新后的交付顺序

### S0：可信目标验证（本轮）

先关闭 Web 可信入口与验证状态矛盾。测试必须包含：恶意 Origin/Host、跨端口来源、空证据、未观察到的应用、未验证启动、不同目标重试及相同目标成功恢复；保留已有成功的多轮工具任务验收。

### S1：M3 记忆生命周期（对应 #10）

- 统一现有 M0–M4 查询门面，记录 `scope/source_task_id/confidence/updated_at`，保持现有 SQLite/JSON 兼容，明确迁移和回滚。
- 将只读访问与学习/同步写入分开；统一 Standard、EphemeralReadOnly、StrictIsolated 的每个入口，包括项目 JSON、习惯与大纲。
- 加入项目过滤、相关性/时效/重要性召回、严格预算、用户纠错和删除；删除后重新召回不可复现被删数据。
- 验收：跨会话真实查询有来源；不同项目不串数据；只读模式无持久化变化；无痕模式零个人数据读取/写入；秘密字段在 SQLite、JSON 和日志均无原文。

### S2：工作空间恢复（对应 #11、#13）

- 在现有 `ProjectRecord` 上演进版本化 Workspace Profile：文档 URI/章节、代码目录、终端 cwd、需变更设置；避免另建资源库。
- 生成增量计划，逐步走 Broker/审批/账本；已打开资源不重复启动，不关闭用户已有程序。
- 每个步骤保存预期谓词与实测结果；设置恢复遵守 ChangeSet 冲突检测，桌面启动等无法完整撤销的影响单独说明。
- 验收：新会话恢复真实项目；不丢子目标；应用缺失/Wayland 状态不可见时返回部分完成；离线天气失败不阻断本地步骤；撤销恢复原设置而不覆盖用户后续编辑。

### S3：受控技能学习（对应 #12）

- 仅从已验证且未撤销的任务轨迹提取候选；移除密钥、具体个人路径与旧审批凭据，参数化引用。
- 用户确认后入库；执行时每一步重新过当前 Policy，不继承来源任务权限。
- 验收：候选可追溯，撤销轨迹不得入库；路径替换、跨项目、过期授权与恶意外部内容均不能绕过策略。

### S4：主动任务与体验（对应 #14–#16）

- 先实现真实文件监听/持久化定时、稳定窗口、事件去重、崩溃恢复和限流，再启用自主执行；默认建议级。
- 触发事件携带来源和权限范围；重启、积压、临时下载文件与任务取消均有确定语义。
- 设置中心 11→5 页保留底层配置兼容；须同时检查 GTK、GNOME 和 Web 的审批、失败与撤销显示。
- AgentBench 分层：意图路由、环境目标成功率、跨会话项目接续、故障/对抗安全。分别报告模拟、宿主机、真桌面数据，不混为一个成功率。

## 4. 工程方法与完成定义

每张任务卡统一采用：**用户输入与目标 → 源码证据 → 不变量 → 最小实现 → 正常/失败/恢复测试 → 实测结果 → 已知边界**。
每次改动复用已有协议和存储，先写可复现失败场景，再改实现；性能工作先测同环境基线，安全与正确性工作以行为证据为主。

合并/提交门槛：格式、clippy、全 workspace 测试；受影响端到端测试；既有 325 条语料和红队；桌面 smoke 能运行则运行。结果另见本轮进度记录，未运行或受环境限制必须明确列出，不沿用历史数字冒充本轮结果。

目标指标分开记录：子目标覆盖率、环境 Goal Success Rate、审批正确率、无痕泄露次数、撤销成功/冲突率、延迟和空闲资源。目标成功率的分母必须包含部分失败、不可观察和超时任务。
