## 1. 产品判断与定位

定位：面向 Ubuntu 桌面的个人 AI 工作入口。用户表达目标，系统结合授权上下文完成跨应用任务，并说明做到什么、还有什么、如何恢复。

首批主要用户：经常处理文档、代码与项目的 Ubuntu 用户。默认中文可用，英文可用；普通用户无需理解模型供应商、CLI、Schema、Token 或权限等级。优先打造可日用的用户态壳层，长期是否演进为专用登录会话，取决于真实使用证据。

当前优势是 Rust 核心、结构化意图、动态能力发现、审批账本、文件撤销和多后端。当前短板是交付可靠性、任务目标证据、上下文生命周期、桌面适配的稳定程度、设置复杂度，以及缺少连续真机验收。

产品北极星：用户每周成功完成并愿意复用的高价值任务数。辅助指标：无帮助完成率、首次成功耗时、重复使用、纠错次数、误报完成率。数据默认留在本地；外发分析需单独选择加入。

## 3. 先做好五条完整用户旅程

| 顺序 | 用户需求 | 必须完成的体验 | 验收 |
| --- | --- | --- | --- |
| 1 | “找到刚才那份文档并打开” | 输入/选中文件/拖入；模糊匹配给候选；打开后显示具体资源 | 找错可立即换选；Wayland 不可见时不猜测 |
| 2 | “把这些下载整理好” | 先给移动列表；批量批准；冲突提示；完成后可撤销 | 不覆盖现有文件；撤销冲突不损伤用户后续编辑 |
| 3 | “继续昨天的论文/项目” | 展示最后进展与来源；用户确认项目；增量打开文档、仓库、终端 | 不重复开应用，不强关现有窗口；各子目标分别验证 |
| 4 | “电脑卡/软件打不开，帮我看看” | 先只读诊断；显示证据和影响；提供可批准修复或系统面板入口 | 缺依赖、无沙箱、权限不足都有具体下一步 |
| 5 | “以后下载完就提醒我整理” | 先建议，再允许限定目录/动作/时段的自动执行 | 临时文件不触发；重启不重复执行；一键暂停和撤销授权 |

文档总结与改写作为旅程 1/3 的能力：预览差异、另存选项、引用来源、内容检查和回滚。语音作为输入增强：按需下载，进度/空间/取消可见，转写先可编辑；不要阻塞文本主路径。

首版优先深测 Files/Nautilus、一个主流浏览器、一个编辑器、LibreOffice 与 WPS 的明确功能子集；其他应用标注“已验证/仅能打开/当前环境不可用”，不把发现数量等同于可靠覆盖。

## 4. 易用性规范

### 首次使用：完成一个真实任务

1. 检测桌面、沙箱、依赖和服务状态，用“可用功能/需要处理”解释结果。
2. 自动列出可用模型；建议一个默认选择，测试连接、工具调用和中文响应。无模型时仍可搜索文件、启动应用和调节设置。
3. 明确选择可访问目录，显示数据是否发送给模型；不能为省步骤默认扫描整个主目录。
4. 引导完成一次“搜索并打开测试文件”；首次上手目标中位数 ≤ 3 分钟，不含大模型下载或用户注册时间。

### 统一入口和反馈

一个快捷键、一个浮窗：顶部当前项目/隐私状态，中间结果，底部输入与附件。支持快捷键修改、键盘全流程、Esc 收起、任务取消、文字缩放、读屏和高对比度。快捷键冲突、输入法、双屏、缩放和焦点恢复纳入真机测试。

五类用户可见状态：需要你确认、正在处理、已完成、部分完成、需要帮助。颜色配文字，不靠轨迹点颜色单独表达。每张任务结果显示产物、未完成项、可用的下一步；技术轨迹按需展开。

取消要说明“已停止后续动作，哪些动作已发生”；已产生副作用不自动假装回滚。审批直接解释文件/应用/外发数据、影响和恢复方式。一次计划可批准限定范围，范围扩大再确认；禁止“信任整个会话”泛化成无限权限。

设置收敛为：**模型与连接、文件与记忆、应用能力、安全与隐私、自动任务**。诊断、日志、上下文预算放入高级区域。旧配置与 RPC 保持兼容，迁移后读回校验。

错误消息要回答“哪里没完成、已有成果是否保留、你现在可以做什么”。不要求用户先贴终端日志才给下一步；支持导出经预览和脱敏的诊断包。

## 5. 目标架构与责任划分

```text
GTK 主入口 / GNOME 快捷入口 / Web 备用界面
                   ↓ 统一版本化 RPC + AgentEvent
意图与上下文：目标拆解、资源消歧、项目范围、隐私约束
                   ↓
任务运行时：步骤依赖、预算、取消、审批暂停、恢复
          ↔ 模型网关（选择、配额、超时、流式、故障隔离）
                   ↓
CapabilityBroker → Policy → 文件/应用/终端执行器
                   ↓
目标检查器 → 证据 → 账本/ChangeSet → 用户结果

共享基础：版本化存储、记忆查询、受控事件队列、观测指标
```

- **交互与业务分离**：GUI 只展示/发起动作；权限、判断、记忆策略均在核心。GTK 为主交付面，GNOME 保持薄入口，Web 复用协议而不复制执行逻辑。
- **沿用单一 Rust 守护进程**，不引入微服务群。只有文档解析、索引、ASR、外部 CLI 等有隔离/资源需求的任务进入受限 worker；崩溃不拖死主交互。
- **TaskGoal 设计增量**：在现有 StructuredIntent/Task 上增加子目标、资源引用、依赖、验收谓词、证据状态。类型字段为建议，先做向后兼容 Schema 设计，不直接替换现有协议。
- **证据不由模型自证**：模型可提出预期，执行器提供可信资源标识，检查器读回内容/设置/窗口身份；记录时间、范围与是否过期。验证失败不得升级为完成。
- **任务与模型解耦**：模型失联保留已完成步骤；纯读请求可有限重试，有副作用须先查账本与环境。重启后恢复到待核验状态，不盲目重放。
- **MemoryService 查询门面**：统一项目范围、来源、置信度、时间和删除；M0 临时状态、M1 会话、M2 文档、M3 偏好、M4 技能保持不同生命周期。按批次迁移既有 JSON/SQLite，保留旧数据备份与回退工具。
- **应用能力契约**：声明支持动作、参数、授权、超时、预期结果、验证方式和撤销范围。通道按动作可靠性选择；已发送写操作后禁止未经核验跨通道重试。
- **安全边界**：持续核验 IPC 调用者与沙箱；Web 同源防护不是本地进程认证。原生 syscall 的 unsafe 边界独立审查；审批令牌一次性且绑定任务/参数/范围。
- **后台执行**：持久化事件 ID、任务幂等键、调度游标与租约，处理时钟变化、睡眠恢复、文件稳定窗口、重启和限流。用户暂停优先级最高。

## 6. 性能目标与优化方法

以下为候选 SLO，先在参考硬件建立基线再冻结：4 核 CPU、8 GiB RAM、SSD、无独显；Ubuntu 24.04 主验证、22.04/26.04 独立兼容验证。记录真实硬件、桌面、内核、模型、构建 SHA 和工作负载。

| 用户感知/资源 | 建议目标 | 测量口径 |
| --- | --- | --- |
| 热启动浮窗到可输入 | P95 ≤ 150 ms | 快捷键事件至首帧可交互，连续 100 次 |
| 冷启动到可输入 | P95 ≤ 1 s | 进程启动至可交互，至少 20 次，不等待模型网络 |
| 本地候选刷新 | P50 ≤ 12 ms，P95 ≤ 30 ms | 预热索引、混合中英文与路径、10,000/100,000 文件分别测 |
| 接收任务的首次反馈 | P95 ≤ 150 ms | 提交至状态反馈，不伪装成模型首字 |
| 直接本地控制 | P95 ≤ 300 ms | 不含应用自身冷启动；另报验证完成延迟 |
| 云端模型首个有效内容 | 选定网络/模型下 P95 ≤ 2.5 s | 单列网络、服务排队、首 token；慢于目标提示可取消 |
| 取消响应 | UI P95 ≤ 100 ms，受控进程停止目标 ≤ 2 s | 从取消到确认，并检查无后续子进程副作用 |
| 空闲资源 | 守护进程 RSS ≤ 80 MiB，10 分钟平均 CPU < 0.5% 单核 | 不含本地模型/ASR；另报进程树总内存与窗口内存 |
| 索引资源 | 增量队列有界；电池模式暂停重扫描 | 分别报告首次索引耗时、峰值内存、队列积压和电量影响 |

措施顺序：加分段计时 → 单机 Release 基线 → 火焰图/热点定位 → 针对性优化 → 同机对照。构建与性能测试串行，避免并发编译污染基准。

优先措施：确定性任务走本地路由；重扫描与文档解析移出 UI 路径；目录变更增量索引；数据库只读不写；能力快照按版本失效；语义召回设预算；worker 池设上限与空闲 TTL；控制队列背压与输出大小。不要对未确认写操作做投机执行，也不要缓存权限决定来换延迟。

模型成本可见：单任务上限、超时、工具调用预算、允许的后端和外发类别。模型切换必须维持当前隐私约束，不能把本地任务静默转到云端。

## 7. 交付阶段与退出门槛

工期不在未知人力条件下承诺。以阶段门槛推进；每阶段结束后才能扩大默认自动执行范围。

| 阶段 | 核心交付 | 退出门槛 |
| --- | --- | --- |
| A 可靠日用 Alpha | 修复/归因 15 项失败；安装/服务契约；任务证据；新手流程；五页设置；快捷入口与取消 | 参考 Ubuntu 主机必须测试全通过；清洁安装/升级/卸载通过；至少 5 位新用户无帮助完成率 ≥80%；无误报完成 |
| B 个人工作 Beta | 记忆生命周期、项目接续、文档预览修改、增量工作区恢复 | 至少 30 个固定跨会话场景，目标成功率 ≥90%；部分失败列明；无痕/删除/项目隔离对抗用例全通过 |
| C 可控主动助手 | 持久化事件调度、用户确认的技能候选、限域自动任务 | 7 天连续运行；睡眠/断网/重启/事件风暴测试；副作用重复次数为 0；能一键暂停与追溯 |
| D 稳定发布 | 支持矩阵、安装包完整性、升级迁移回退、说明文档和诊断工具 | 参考设备 SLO 达标；至少 10 位试用者连续 2 周反馈；关键旅程无帮助完成率 ≥90%；无未处理 P0 |

用户研究样本是形成改进方向的试点规模，不是统计意义的全人群保证。“好用”以真实任务完成、纠错成本和持续复用验证，不以设计文档承诺。

## 9. 完成定义

一项功能只有同时具备：用户入口、正常完成、可理解失败、权限/隐私、资源预算、恢复方式、环境证据和验收记录，才能标记完成。每个 PR 应绑定上表工作包、前后行为、测试证据和未覆盖环境。

M1/M2 的历史“完成”不等于整个产品已日用就绪。产品状态与模块进度分别维护。所有指标要说明统计分母；失败、取消、不可观察和未授权各自计数，不能从目标成功率中静默移除。
